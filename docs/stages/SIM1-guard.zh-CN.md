# SIM1-02 — 执行钩子处的接收端守卫与租约

日期：**2026-10-05**。运行：`20261005T063753Z-sim1-02`。[English report](SIM1-guard.md)。协议：[roboracer.guard/1](../../integration/autodrive/sim1/PROTOCOL.md#roboracerguard1--receiver-guard-sim1-02)。

**SIM1-02 通过。** 守卫在仿真器内、每个执行步之前立即运行。它对每条指令依次校验：上电（arming）纪元、来源、有序序号、生命周期，以及仅凭自身时间戳计算的时钟上界。只有租约有效时才应用指令。守卫模式下关闭了遗留、手动与 GUI 控制路径，并对每次接受、拒绝、应用与状态变化给出确认。

全部断电（disarmed）P1a 指令、时钟与故障用例在三个独立的全新进程中均通过。在六次实时运行共 0.41 M 个物理步中：

- 没有任何一步出现非零输出、扭矩或转向；
- 只有在上电状态下被接受、且尚未过期的指令才会到达执行钩子。

两个 60 秒观测窗口转发了每条新请求，无拒绝、无过期。**车辆未运动**：全程开启零输出联锁，所有被接受的指令均为精确零。运动测试仍须等待 SIM1-05 运动协议。

**接收端时钟上界。** 桥接现在还会报告它收到所回复帧的时刻。仿真器只用自身的发射与接收时间戳界定时钟偏移，因此发送方无法通过上报自己的估计来收窄上界。截止时间映射到最早可能的仿真器时刻；出现不相交的新区间即视为时钟跳变，会话进入故障。

用模拟接收端离线运行场景脚本时发现：第一版上界只用 ping 时刻，因桥接每次回复前都有 100 ms 节拍延时，宽度约 150 ms。在该上界加 500 ms 租约下，只要漏掉一次回复，租约就会过期。加入帧接收时刻后，上界收窄到两段传输时间，实测 p50 约 47 ms。

**暂定参数。** 租约 **1 s**（接收端上限与请求最长寿命）；时钟上界宽度不超过 **400 ms**；只计最近 **2 s** 内的交换。这些取值让原有约 3.9 Hz 的锁步回路能容忍一次漏回复。它们是测试参数，不是已验证的运动上限；实际取值在 SIM1-05 冻结。

## 6. 保留的失败

1. **`build-console-failed-series-check.log`：** 第一次构建在 Editor 启动前即被拒绝。`git apply --check` 拿补丁 02 去对照未打补丁的树。预检现改为在临时索引上按顺序应用整个补丁系列。工程未被修改。
2. **`scenario-a`，第一个场景进程：** 14 个契约／时钟／遗留阶段全部通过，播放器跟踪也通过（62,786 步，0 非零，65 条接受并应用）。三个测试工具缺陷导致其失败：
   - 合成 GUI 点击丢失且未重试；
   - 监督者丢失检查把杀死前已缓冲请求的合法接受也算了进去；
   - Devkit 丢失等待期望租约过期，而断开（7.4 ms）其实已先清除租约，随后又读取了一行仍在写入的跟踪。

   三者均已修复，并在模拟场景中加入回归覆盖。`scenario-b` 第 1 次运行中首次点击再次丢失；重试被阻止并记入日志。
3. **`observe-failed-connect`：** Connect 点击丢失（与 SIM0、SIM1-01 相同的间歇问题），运行触发有界的启动超时。守卫跟踪显示 174,890 步全为零，无任何接受。其清理暴露出一个缺陷：监督者在从未被读取的套接字上阻塞发送，只能 SIGKILL。现改为非阻塞发送并统计丢弃数。这是场景运行与观测运行之间 `autodrive_guard.py` 的唯一改动。
