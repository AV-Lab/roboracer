## 2. S2-03 — recording and open-loop replay (built; live recording check passed)

**Delivered** (`f6ba4e2`):
- **Recorder.** `AutoDriveBridge.message_listener`, an optional hook. With the default `None`, the bridge is unchanged. `scripts/roboracer_inputs.py` `InputRecorder` writes every raw Devkit message, in processing order with the bridge's arrival time, to `plugin-inputs.jsonl` (schema `roboracer.inputs/1`).
  - Scans are stored as float32 bytes, exactly as published.
  - The file is bounded at 64 MB per run and marked truncated past that.
  - The recorder never raises into the bridge; failures are counted instead.
  - Enabled with the runner flag `--record-inputs`.
- **Replay** (`roboracer_inputs.py replay`). It is labelled open-loop and never counts as a lap.
  - Recorded messages go through a fresh `SnapshotAssembler` (the plugin's own code). Each snapshot is compared field by field with the live `plugin-snapshots.jsonl`: identity, scan hash, pose, encoders, stamps, clock bound and skew.
  - When ticks carry controller outputs, each tick's sensor frame is rebuilt through `AutoDriveBridge.get_sensor_frame` and run through the same controller class and parameters. The command is compared with the live tick.
- **Analytical fixtures** (`roboracer_inputs.py fixtures`). Synthetic recordings go through the file format, the assembler and baseline A. All three pass; tolerance 1e-6 follows the float32 point representation.

| Fixture | Expected (closed form) | Replayed |
| --- | --- | --- |
| Symmetric corridor, half-width 1.0 m | speed 0.3, steer 0 | 0.3 − 6e-15, −1.3e-14 |
| 1.0 m ring with a no-return opening at +20…+80° | α = 34.25° (after 57-beam disparity extension), steer 0.349708, speed 0.125 | 0.125, 0.349708 (diff 1e-14) |
| 0.45 m dead end | speed 0 (steer not determined) | 0 |

A first fixture set wrongly expected straight-ahead steering in equal-range rings. Equal finite ranges tie only up to float32 rounding, so the tie-break is noise. The fixtures were rebuilt so that every checked value is determined.

## 3. S2-01/02 — unattended batches and recovery (built; stationary live checks passed)

**Decisions:** "approve D20 A, D21 A, D22, D23, D24" (2026-10-09).

**Delivered** (`6fe985d`, `99c05b7`, `7576750`, `ffecffa`):
- **Guard driver `batch` mode** (`autodrive_guard.py`). Each episode:
  1. arm in a new epoch;
  2. from episode 2 on, replay the previous epoch's last forwarded request, which must be rejected `stale-epoch` (no stale reapplication);
  3. forward requests until the AVLite stage reports the episode finished (stationary: a fixed window);
  4. require exactly one final lease expiry (stationary: none), with no rejection and no fault;
  5. disarm;
  6. GUI Reset, then check the scene-load disarm and episode +1.
- **Multi-episode AVLite stage** (`StackStage`). It reports each finished episode in `stage-episodes.json` and starts the next only after a scene load. From episode 2 on, it starts only once the guard has been seen not armed in the new episode, so an "armed" left over from the previous episode never starts it.
- **Automated pre-Connect check** (`roboracer_uicheck.py`, D21 A). It compares the text pixels of five regions against a reviewed reference, in the same review format as before, so the Connect path keeps all its window and hash checks. Up to 8 mismatched pixels are allowed per region; measured: 0. **Readiness after each reset**, before any arm:
  - spawn offset ≤ 0.010 m;
  - yaw within 1° of the first spawn;
  - wheels still;
  - guard not armed and no fault.

  A failure raises "Initialization failed".
- **Orchestrator** (`roboracer_batch.py`). It implements the recovery ladder: a fresh player after a failed session, and the batch ends if that restart fails too. It also enforces the wall cap, counts every attempted episode (a failed initialization included), lists every recovery action, scores each driving episode independently, and records the longest healthy streak.
- **Supervisor fix** (`6fe985d`). No encoder-speed sample is taken across an episode change.
  - **Correction:** I first described this as a failure that would starve the speed loop for about 125 s after every reset. That was wrong: the old code skipped one frame and then resumed.
  - **The real defect** was narrower. After a short episode, one bogus cross-reload sample could trip the overspeed rule for one frame.
  - The new test fails on the old code and passes on the new.
- **Tests:** script suite 155/155 (batch driver ×3, batch stage ×4, UI check ×5, orchestrator ×5 among them) and plugin suite 44/44.

## 4. M2 baseline part 1 — first unattended 3-lap batch (failed: 1/3 healthy; fixed; rerun needs approval)

**Approval:** "reference OK; approve the 3-lap batch" (2026-10-09). The reference is now user-reviewed (D21). Evidence: `artifacts/s2/20261009T062247Z-m2-batch1/` (manifest).

| Episode | Result |
| --- | --- |
| 1 | **healthy**: finished on distance (33.1 m), 1 lap of 122.9 s, min clearance 0.104 m, no contact or off-track. Same as the M6 laps. |
| 2 | **failed**: the stage ran to its 200 s limit; the car moved 11 mm |
| 3 | **failed**: the same |

**What worked:**
- The whole batch ran unattended in 596 s.
- 3/3 automated Connect checks passed at 0 px; 2/2 resets passed readiness (offset 1 mm, yaw 0.0°), with one Reset click and one Connect click each time.
- Every process exited 0; the player is unchanged.

**Root cause.** The supervisor latched into **inhibited, feedback-lost**, which is sticky, on the first request of episode 2, and rejected all 4,135 later requests.
- The speed loop checks feedback age before anything else, even for a zero target.
- A GUI Reset leaves several seconds without telemetry, so the first request of the next episode met feedback more than 0.9 s old.

This was a **safe failure**: nothing was forwarded, the guard applied nothing, and the car stayed at the spawn.

**Not caught earlier.** Single laps never cross a reset. The stationary batches run no speed loop. So my stationary checks did not cover this path.

**Fix** (`939b7fd`). A new simulator episode restarts the speed loop as at start-up: "no feedback yet", zero throttle.
- The new episode is detected from the request's observation episode and from the feedback samples, which now carry their episode, so arrival order does not matter.
- Late samples from an earlier episode are ignored.
- Old feedback **within** an episode is still detected as lost.
- 4 new tests; plugin suite 48/48, script suite 155/155.
- The supervisor status now reports `speed_loop.episode_restarts`.

**Replay on driving data, the open S2-03 item.** Batch 1's recording (16,488 messages, all three episodes) was replayed in three fresh processes:
- **2,747/2,747 snapshots identical**;
- **5,392/5,392 GapFollowController commands identical**, worst difference 0.0.

The D24 exact-equality criterion holds on a lap.

## 5. Batch rerun with the fix (2/3 healthy; the third stopped by a real simulator stall)

**Approval:** "approve the rerun of the 3-lap batch" (2026-10-09). Evidence: `artifacts/s2/20261009T070755Z-m2-batch2/` (103-file manifest).

| Episode | Result |
| --- | --- |
| 1 | **healthy**: 1 lap of 123.0 s, min clearance 0.105 m, no contact or off-track |
| 2 | **healthy**: 1 lap of 123.8 s, min clearance 0.105 m. The speed loop restarted at the episode, as fixed. |
| 3 | **failed**: 0.65 m into the lap, telemetry stopped. The stack aborted ("no new observation for 0.60 s"). The **hang watchdog killed the player 2.10 s after the last frame (containment, not a stop).** No episodes remained, so no fresh player was started. |

- **The fix works.** The speed loop restarted twice (`episode_restarts` 2), and lap 2 drove normally after the Reset.
- **Unattended.** 3/3 automated Connect checks at 0 px; 2/2 readiness checks; one click each time. Batch wall time 335 s.

**The stall** — the first one seen without injection, in about 40 driven runs since S1:
- **Player at detection:** alive but **sleeping**, with 73 threads waiting on locks and none running. It was not stopped by a signal.
- **GPU:** use dropped from 42 % to 0 % about 2 s before detection, so rendering stopped.
- **Devkit bridge:** it had counted a reply to every frame (1,652/1,652). It counts the reply just before handing it to Socket.IO, so this does not prove the last reply left the process.
- **Unity log:** nothing unusual near the stall; the only thread-abort messages come from the two scene reloads.
- **Reading:** this looks like the stock lock-step exchange stalling, with the player waiting for a reply. Whether the reply left the bridge, or was lost in transport or in the player's socket thread, cannot be decided from what was recorded.
- **New diagnostics** (`a3c251b`). The bridge now records when each reply is handed to Socket.IO and when that call returns, and the hang record keeps those times plus the bridge's thread states.
  - Checked on a deliberate stationary hang: the last reply returned 58.8 ms after the last frame arrived, so the player was the side that stopped.
  - The first check attempt failed only because three synthetic Connect clicks were dropped. The desktop was not locked and nothing was left over; that attempt is retained.
- **Consequence for S2.** Containment and the recovery ladder handle such stalls, but each costs the episode. "Ten consecutive healthy episodes" (M2 acceptance) is at risk if stalls recur. Their rate must be measured in the baseline before budgets are proposed.

**Replay ×3 fresh processes:** 1,651/1,651 snapshots and 2,815/2,815 controller commands identical.
